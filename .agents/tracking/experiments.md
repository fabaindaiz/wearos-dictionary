# Experiments — what would confirm or falsify a note

**Every note ends with the experiment that would settle it. This is where those experiments
are queued, run and recorded**, so that `confidence` is earned by data rather than by prose,
and a note contradicted by evidence goes to review and is revised or retired (`../knowledge/README.md`, *The
lifecycle of a note*).

Cheapest first. When one is run, record the date, the repository (by a neutral kind of software,
never by name, and never with a carrier id beside that description), the number as a ratio or an
order of magnitude, and the verdict — **confirms**, **moves the boundary**,
or **falsifies** — then apply it to the note in the same change.

| 2026-09-22 | nested-partial-update-replaces | a transactional backend on a hosted document store | the client's own update-mask builder called offline on three payloads, and the write layer scanned for update literals | a nested payload `{'a': {'b': 1}}` produces the mask `['a']` — the **parent** field, so the whole map is replaced and its siblings are lost — while the dotted payload `{'a.b': 1}` produces the mask `['a.b']`. Two keys under one parent behave like the first. In the write layer, the update literals use dotted keys, none carries a non-empty nested map, and the one nested value is an empty map, a deliberate clear | **confirms**, and documents the semantics for this client, which is what the queued experiment asked per client. This repository has no accidental occurrence: where it means merge it writes a dotted path |
| 2026-09-22 | fail-closed-defaults | the same backend | a probe that imported one utility module with no environment set, then a count of configuration reads without a default | the import refused twice in a row, each time naming the missing variable, before any code ran. About four in five configuration reads, across dozens of modules, have no default and raise at import; the rest have one | **confirms the mechanism half** and **names a boundary the queued experiment cannot cross here**: the question "how often does a service start with a required variable unset" has the answer *never* by construction — it does not start. What is unpriced is the other half, the reads that do have a default |
| 2026-09-22 | untrusted-package-is-parsed-never-loaded | a browser-target client application whose content travels as zip packages, each file listed with its size and hash in an index inside the zip | three forged packages, against the application's own reader and against the second implementation of the same rules that runs before the engine is opened: (1) the central directory understating one entry's unpacked size by tens of megabytes; (2) the same lie told in the directory and in the index together; (3) twenty directory entries pointing at one local header, declaring more than the total unpacked limit | (1) refused at open after a few kilobytes, the entry named; (2) accepted at open, the read returned empty and named the entry, peak allocation within a fraction of a percent of the honest package's — the understated entry was never allocated; (3) refused at open after a couple of kilobytes, with a message naming the unpacked total and the limit | **confirms**, and the declared-size gap does not open: the bound holds because the decompressor stops at the declared size, so a lie buys no allocation, and because two independent declarations — the directory and the hashed index — have to agree. The second implementation agreed on (3) word for word and raised an uncaught archive error on (1) and (2) instead of naming a problem; that half is a candidate, and a defect in that repository's own roadmap |
