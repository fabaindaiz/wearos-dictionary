# Proposal: repeated-friction-becomes-a-build-check

A friction that repeats is turned into a build-time or commit-time check, not another line of prose. Count the recurrences from the record; when the rule was in context and the failure happened anyway, the next rung is a mechanism that refuses the bad state before it exists, probed once to see it fail, and kept honest by a gate that fails where the mechanism is not installed.

## Evidence

One carrier, one owner. Two cases. First, new bundled data shipped under the old version number, so the application opened the previous data: four incidents counted from the version file's own comments, after which the build was made to fail when the data differs from a lock under an unchanged version, with a gate check that fails when the version moved and the lock did not; the guard fired once within the window that followed, on a real rebuild. Second, a document count that the prose rule said to refresh in each intermediate commit broke twice with the rule loaded, the second time on a two-commit series; it became a pre-commit hook that runs the audit over the staged snapshot, probed by staging a test without its counts and seeing four counts refused, with a gate check that fails on a clone where the hook is not enabled. Literature: the candidate's own; no new source consulted.
